# Менеджер проєктів і задач: специфікація та ухвалені рішення

Тема: «Менеджер проєктів і задач». Мова: Python 3.14, інтерфейс: Tkinter,
лише стандартна бібліотека. Архітектура: MVP.
Це робочий документ: з нього пишуться підрозділи 2.1–2.5 записки.
Якщо рішення в коді змінюється, спочатку правлять цей файл, потім записку і діаграму.

## 1. Рішення, ухвалені студентом

| № | Питання | Рішення | Обґрунтування |
|---|---|---|---|
| 1 | Зв’язок задачі з виконавцем | Задача зберігає посилання на об’єкт `Member` | Природна для ООП модель; у JSON зберігається `assignee_id`, зв’язування виконується під час імпорту |
| 2 | Видалення учасника з задачами | Задачі видаляються каскадно, перед цим користувач підтверджує дію (у тексті вказано кількість задач) | Задача без виконавця не допускається; збігається з тестом із завдання |
| 3 | Прогрес елемента | За статусом (без урахування годин) | Просто пояснити й перевірити |
| 4 | Список учасників | Спільний для всіх проєктів, зберігається в сервісі; `Project` учасників не зберігає | Один учасник може працювати в кількох проєктах |
| 5 | Прогрес `Milestone` | Як у `Bug`: `DONE` = 1, інакше 0 | Віха досягнута або ні; різниця між класами за змістом, правило можна змінити окремо |
| 6 | Редагування задач | Лише через `Project.update_item()` (з сервісу й презентера) | Правила проєкту (межі дат, унікальність назви) перевіряються в одному місці |
| 7 | Зміна дат проєкту | Заборонена, якщо дедлайни наявних задач виходять за нові межі (`ValueError`) | Цілісність даних |
| 8 | Унікальність назв | Назва задачі унікальна в межах проєкту, назва проєкту унікальна серед усіх проєктів; порівняння без урахування регістру | Вимога завдання «унікальна назва» |
| 9 | Ідентифікатори | Глобально унікальні для задач; нові видає сервіс за правилом «максимальний наявний + 1» | Простіші звіти й фонові операції; номер останньої видаленої задачі може використатися повторно |
| 10 | Помилка в одному записі файлу | Відхиляється весь файл, наявні дані не змінюються | Цілісність; простіше пояснити й перевірити |
| 11 | Квадратична перевірка в `Project.add_item` | Залишена свідомо, обмеження задокументоване (див. розділ 10) | Задачі розподіляються між проєктами; замірі потоків виконано на 100 проєктах |

## 2. Перелічення

| Елемент | Значення в JSON | Підпис в інтерфейсі |
|---|---|---|
| `Status.TODO` | `"todo"` | До виконання |
| `Status.IN_PROGRESS` | `"in_progress"` | У роботі |
| `Status.DONE` | `"done"` | Виконано |
| `Priority.LOW` | `"low"` | Низький |
| `Priority.MEDIUM` | `"medium"` | Середній |
| `Priority.HIGH` | `"high"` | Високий |

- Значення в JSON завжди малими літерами; регістр суворий (`"TODO"` відхиляється).
- Невідоме значення під час імпорту дає `ValueError`, який перетворюється на `DataFormatError`.
- Підписи інтерфейсу зберігаються у `views/labels.py` (модель про інтерфейс нічого не знає).
- Порядок для сортування: пріоритет `LOW < MEDIUM < HIGH`, статус `TODO < IN_PROGRESS < DONE`.

## 3. Модель класів (`models/`)

- `Trackable(ABC)`: `progress() -> float` (від 0 до 1), `is_overdue(today: date) -> bool`.
- `WorkItem(Trackable)`: абстрактний; поля `id`, `title`, `assignee`, `priority`, `status`,
  `deadline`, `estimate_hours`; `progress()` залишається абстрактним, `is_overdue()` реалізовано
  один раз, `item_type` повертає ім’я класу.
- `Task`, `Bug`, `Milestone(WorkItem)`: конструктор успадкований, перевизначено лише `progress()`.
- `Member`: `id`, `name`, `role`.
- `Project`: `id`, `name`, `start`, `end`, список елементів; агрегує `WorkItem`.
  Методи: `add_item`, `remove_item`, `update_item`, `items` (копія списку), `progress`,
  `overdue_items(today)`, `remove_items_for_member`. `Project` не наслідує `Trackable`
  (`is_overdue` для проєкту не має змісту).

### Правила прогресу

- `Task`: `TODO` = 0; `IN_PROGRESS` = 0,5; `DONE` = 1.
- `Bug` і `Milestone`: `DONE` = 1, інакше 0.
- `Project.progress()`: середнє арифметичне `progress()` усіх елементів; порожній проєкт = 0.
  Проєкт не знає типу елемента й просто викликає `progress()` (поліморфізм).

### Прострочена задача

Дедлайн раніший за задану дату і статус не `DONE`. Якщо дедлайн дорівнює даті, задача
не прострочена. Дата передається параметром (`today`), а не береться всередині методу,
тому граничні випадки перевіряються в тестах.

## 4. Валідація

Усі помилки валідації в моделях і сервісі: `ValueError`. Файлові помилки: `DataFormatError`.

| Поле | Правило |
|---|---|
| `id` (Member, WorkItem, Project) | ціле число більше нуля, `bool` не допускається |
| `name`, `role`, `title` | рядок, непорожній після `strip()` |
| `assignee` | об’єкт `Member` (існування в списку учасників перевіряє сервіс) |
| `priority`, `status` | елементи `Priority`, `Status` |
| `deadline` | `date`, `datetime` не допускається |
| `estimate_hours` | `int` або `float`, більше нуля, скінченне (`nan`, `inf`, `bool` не допускаються) |
| `Project.start`, `Project.end` | `date`; початок не пізніше завершення |
| дедлайн задачі | у межах `[start, end]` проєкту, межі включно |
| назва задачі | унікальна в проєкті без урахування регістру (`casefold`) |
| `id` задачі | унікальний (у проєкті перевіряє `Project`, між проєктами сервіс і репозиторій) |

Редаговані поля `Project.update_item`: `title`, `assignee`, `priority`, `status`, `deadline`,
`estimate_hours`. Змінити `id` або тип не можна. Зміна атомарна: якщо одне з полів відхилено,
уже змінені повертаються до старих значень. Така ж атомарність у `update_member` і `update_project`.

## 5. Шари та структура проєкту (MVP)

```
project_manager/
  main.py            точка входу, журнал, збирання застосунку
  models/            enums, trackable, work_item, task, bug, milestone, member, project
  repository/        json_repository (JSONRepository, DataFormatError), xml_report (XmlReportWriter)
  services/          project_service (ProjectService), background_tasks (BackgroundTasks)
  presenters/        main_presenter (MainPresenter, протокол MainView)
  views/             main_window, dialogs, labels
  tools/             generate_data, make_broken_files, benchmark, benchmark_load
  tests/             unittest
  data/              приклади даних, результати замірів
  DESIGN.md  AI_LOG.md  README.md
```

- Імпорти абсолютні від кореня проєкту (`from models.member import Member`); у кожній папці `__init__.py`.
- Презентер не імпортує `tkinter`, тому тестується без вікна (клас `FakeView`).
- Усі зміни даних виконуються лише через `ProjectService`. Прямі виклики `project.add_item(...)`
  з презентера обходять блокування й правила сервісу, тому не допускаються.

## 6. Сервіс (`ProjectService`)

- Стан: списки учасників і проєктів; доступ під `threading.RLock`; властивості `members` і
  `projects` повертають копії.
- **Чому `RLock`:** `delete_member` викликає `count_member_items` під тим самим блокуванням;
  звичайний `Lock` у такому випадку завис би.
- Учасники: `add_member`, `update_member` (атомарно), `count_member_items`, `delete_member`
  (каскад, повертає кількість видалених задач).
- Проєкти: `add_project`, `update_project` (атомарно: назва, початок, кінець), `delete_project`.
  Унікальність назви перевіряється серед усіх проєктів.
- Задачі: `add_item(project, item_type, ...)` створює об’єкт за типом (`Task`, `Bug`, `Milestone`),
  видає новий `id`, перевіряє, що виконавець є в списку учасників; `update_item`, `delete_item`.
- `snapshot_items()` повертає пари (проєкт, задача) для фонових операцій.
- `find_items(project, text, status, priority, assignee, sort_by, descending)`:
  пошук за підрядком у назві без урахування регістру; фільтри поєднуються через «і»;
  `None` і порожній рядок означають «без фільтра»; сортування за `deadline`, `title`, `priority`,
  `status` з другим і третім ключем (назва, `id`) для стабільного порядку; повертає новий список.
  Вибірку виконано поза блокуванням (знімок береться під ним), щоб не затримувати фонові операції.
- Файли: `load_file` розбирає файл поза блокуванням і підміняє дані лише після успіху
  (інакше дані не змінюються); `save_file` і `export_overdue_report` тримають блокування на час запису.
- Після `load_file` усі раніше отримані об’єкти `Member` і `Project` стають недійсними
  (сервіс відхиляє їх як «чужі»). Презентер заново запитує списки й скидає вибраний проєкт.

## 7. Дані та файли

### JSON (`JSONRepository`)

Корінь: `members` (`id`, `name`, `role`) і `projects` (`id`, `name`, `start`, `end`, `items`).
Елемент: `type` (`Task`, `Bug`, `Milestone`), `id`, `title`, `assignee_id`, `priority`, `status`,
`deadline`, `estimate_hours`. Дати суворо `YYYY-MM-DD`.

Порядок читання: файл читається й розбирається в окремих `try`; перевіряється структура;
спочатку створюються учасники, потім проєкти й елементи; виконавець шукається за `assignee_id`;
елементи додаються через `Project.add_item()`, тому правила проєкту діють і під час імпорту.
Помилка повідомляє місце («проєкт №2, елемент №5»). Повертається результат лише після
успішного розбору всього файлу.

Додатково відхиляються: повтор `id` учасника, проєкту, задачі (між проєктами), повтор назви
проєкту (без урахування регістру), `estimate_hours` рядком або не більше нуля, неіснуюча дата,
формат дати, відмінний від `YYYY-MM-DD`.

Збереження: UTF-8, `ensure_ascii=False`, `indent=2`; запис у тимчасовий файл у тій же папці
та `os.replace` (при збої наявний файл не пошкоджується); тимчасові файли видаляються.

### XML-звіт (`XmlReportWriter`)

```
report[date]
  project[id, name, overdue_count]
    item[id, type]: title, assignee, deadline, status, priority, days_overdue
```

- Проєкти без прострочених задач потрапляють у звіт з `overdue_count="0"`.
- Порядок задач такий самий, як у проєкті.
- Статус і пріоритет у звіті це значення (`"todo"`), не підписи.
- Дата звіту (`today`) передається параметром; запис через тимчасовий файл і `os.replace`.
- Лише запис, читання XML не реалізовано.

## 8. Фонова обробка (`BackgroundTasks`)

- Параметри: `max_workers` (за замовчуванням 4), `chunk_size` (500).
- Кожна операція запускається в окремому потоці-координаторі (`daemon`); обчислення частин
  виконує `ThreadPoolExecutor`.
- **Координатор, а не колбеки:** координатор збирає результати частин і об’єднує їх сам,
  тому спільного змінного словника немає й гонок під час злиття немає.
- Повідомлення: `Message(kind, operation_id, data)`, види `progress`, `result`, `error`, `done`.
  Дані в повідомленнях прості (числа, словники, списки); об’єкти предметної області не передаються.
  Повідомлення `error` кладеться в чергу раніше за `done`; `done` надходить завжди (блок `finally`).
- Операції:
  1. імпорт: один виклик `load_file`; прогрес невизначений (`total=None`);
     результат `{"members": N, "projects": M}`;
  2. навантаження учасників: частини по `chunk_size` задач; у кожній частині години невиконаних
     задач за виконавцями; результат `{"workload": {member_id: hours}}`;
  3. пошук прострочень: результат `{"overdue": [{"project_id", "item_id", "days_overdue"}]}`;
     `today` передається параметром.
- Закриття: `shutdown()` викликає `executor.shutdown(wait=False, cancel_futures=True)`;
  координатор перевіряє скасовані частини з таймаутом, тому не зависає.
- Потоки не звертаються до віджетів. Вікно опитує чергу через `after()` кожні 100 мс.
- Блокування: `RLock` сервісу захищає списки; звичайний `Lock` захищає лічильник активних операцій.
- Помилка в частині перехоплюється, записується в журнал і передається повідомленням `error`.
- `poll()` читає все накопичене; `get_message(timeout)` призначений для скриптів вимірювання,
  в застосунку чергу читає лише презентер через `poll()`.

## 9. Презентер і вікно

### Контракт View (`MainView`)

Презентер викликає: `show_projects`, `show_members`, `show_items`, `show_error`, `show_info`,
`confirm`, `set_busy`, `show_progress`, `stop_progress`, `show_workload`, `show_overdue`, `close`.
Вікно викликає методи презентера: `select_project`, `set_filters`, `set_sort`, `add_*`, `update_*`,
`delete_*`, `import_file`, `export_json`, `export_xml_report`, `calculate_workload`, `find_overdue`,
`process_messages`, `on_close`. Тест `ViewContractTests` перевіряє, що `MainWindow` реалізує
кожен метод протоколу з тією ж сигнатурою.

### Правила презентера

- `refresh()` єдине місце синхронізації вікна з даними; викликається після кожної зміни.
- Дата для користувача `YYYY-MM-DD` (суворо); розбирає презентер, сервіс приймає лише `date`.
  Години приймають кому як десятковий роздільник.
- Підписи в `Combobox` локалізує вікно; презентер працює зі значеннями перелічень.
- Видалення учасника, проєкту й задачі виконується після підтвердження; для учасника в тексті
  вказано кількість задач.
- Редагування, імпорт, експорт і фонові операції блокуються, поки виконується фонова операція
  (повідомлення «Зачекайте завершення поточної операції.»). Перегляд, пошук, фільтри, сортування
  й вибір проєкту не блокуються.
- Читання даних у `refresh()` виконується без блокування сервісу: це безпечно, бо під час фонової
  операції редагування заблоковано.
- Після імпорту вибраний проєкт скидається. Стартовий імпорт (`announce=False`) не показує
  інформаційного вікна, помилку показує завжди.
- Чужі `operation_id` ігноруються; помилка обробки одного повідомлення не зупиняє наступні;
  збій у вікні не перериває опитування (`after` перепланується в `finally`).
- Закриття під час операції запитує підтвердження, потім викликає `shutdown()` і закриває вікно.
- Необроблені винятки обробників Tkinter: `report_callback_exception` у `main.py` пише в журнал
  і викликає `presenter.show_unexpected_error`.

### Вікно (`MainWindow`)

Меню «Файл» (імпорт JSON, експорт JSON, XML-звіт, вихід) і «Операції» (навантаження, прострочені);
ліворуч проєкти й учасники, праворуч пошук, фільтри й таблиця `ttk.Treeview`; рядок стану й
`ttk.Progressbar` (визначений і невизначений режими). Прострочені задачі підсвічено. Сортування
за клацанням по заголовку (стрілки ▲ ▼). Затримка пошуку 250 мс. Під час операції кнопки й пункти
меню заблоковано. Форми проєкту, учасника й задачі це модальні `Toplevel`; при помилці форма
лишається відкритою.

## 10. Журнал, запуск, відомі обмеження

- Журнал: `tasks.log` у корені проєкту (UTF-8, рівень INFO); налаштовується тільки в `main.py`.
  Записуються запуск і закриття, операції сервісу (CRUD, файли, каскадне видалення з кількістю),
  фонові операції (номер, кількість частин, потоки, час), помилки репозиторіїв.
- Запуск: `python main.py [--file шлях] [--empty]`; стартовий файл `data/projects.json`
  завантажується у фоні.
- Тести: `python -m unittest discover -s tests -t . -v` (185 тестів на момент останнього прогону;
  тести вікна пропускаються, якщо немає дисплея).

Відомі обмеження:
1. `Project.add_item` виконує лінійні перевірки (за об’єктом, `id` і назвою), тому складність імпорту
   квадратична для одного проєкту. Заміри завантаження (один прогін): 10 000 задач в одному проєкті
   69,4 с; 10 000 задач у 100 проєктах 1,1 с; 12 000 задач у 100 проєктах 1,3 с. Імпорт виконується
   у фоні, інтерфейс не зависає. Покращення: множини `id` і назв у `Project` (перевірка за O(1)),
   які оновлюються в `add_item`, `remove_item`, `update_item`, `remove_items_for_member`.
2. Нові `id` видаються за правилом «максимальний + 1»: номер видаленої останньої задачі
   може використатися повторно.
3. Редагування обходить правила проєкту, якщо викликати сеттери `WorkItem` напряму; захист діє
   за домовленістю (редагування лише через `Project.update_item`).
4. Назви проєктів порівнюються через `lower()`, назви задач через `casefold()`; для кирилиці та
   латиниці результат однаковий.

## 11. Замірювання потоків

Параметри: Python 3.14.10 (CPython), GIL увімкнено, 4 логічні ядра, Windows 10,
12 000 задач, розмір частини 500 (24 частини), 20 повторів + 1 прогрівальний, показано медіану.
`T1` це пул з одним робочим потоком (а не цикл без пулу), тому накладні витрати на пул, чергу й
повідомлення однакові для всіх `n`. `S = T1/Tn`, `E = S/n`.

| Операція | n | Медіана T, с | S | E |
|---|---|---|---|---|
| Навантаження учасників | 1 | 0,0090 | 1,00 | 1,00 |
| | 2 | 0,0092 | 0,98 | 0,49 |
| | 4 | 0,0093 | 0,97 | 0,24 |
| | 8 | 0,0095 | 0,95 | 0,12 |
| Пошук прострочень | 1 | 0,0165 | 1,00 | 1,00 |
| | 2 | 0,0164 | 1,00 | 0,50 |
| | 4 | 0,0166 | 0,99 | 0,25 |
| | 8 | 0,0172 | 0,96 | 0,12 |

Висновок для записки: обидві операції суто обчислювальні, а за наявності GIL потоки виконуються по
черзі, тому прискорення немає (`S ≈ 1`), а накладні витрати незначно знижують `S` зі зростанням `n`.
Загальний час 9 і 16 мс, відмінності порядку 0,01 мс лежать у межах шуму. Багатопотоковість у
застосунку потрібна, щоб інтерфейс не зависав під час імпорту й обчислень, а не для прискорення.
Для очікування введення-виведення потоки допомагають, для чистих обчислень на Python ні.
Результати не підганялися, штучних затримок немає.
